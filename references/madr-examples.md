# MADR Examples Reference

Two worked examples for the adr-generator skill. Use these to calibrate what good vs bad retroactive MADR output looks like.

---

## Example 1 — Good: Alternatives Evidenced in Diff

This is what a well-evidenced retroactive MADR looks like. The diff showed `moment.js` being deleted and `date-fns` being added. The commit message said "replace moment.js with date-fns to reduce bundle size". Both the old approach and the new one are directly visible — so the Considered Options section is populated legitimately.

```markdown
# Replace moment.js with date-fns for date formatting

## Status

Accepted

> Note: This ADR was retroactively generated from commit history by adr-generator.
> Rationale accuracy depends on commit message quality. See linked commits to verify.

## Context and Problem Statement

The application was using moment.js for all date formatting and parsing. Moment.js is
a large library (~67KB minified) that is no longer actively maintained. The bundle size
was contributing to slow initial load times on mobile.

## Decision Drivers

- Bundle size reduction (moment.js was the third-largest dependency)
- moment.js is in maintenance mode as of 2020

## Considered Options

- moment.js (existing approach — removed in this change)
- date-fns (chosen — added in this change)

## Decision Outcome

Chosen option: **date-fns**, because the commit message explicitly states "replace
moment.js with date-fns to reduce bundle size" and the diff confirms moment.js was
fully removed.

### Positive Consequences

- Reduced dependency on an unmaintained library
- Tree-shakeable — only imported functions are bundled

### Negative Consequences / Trade-offs

- date-fns uses a different API from moment.js — 14 call sites were updated in this change

## Links

- Commits: a3f1c2d, b8e4f19
- Merge/PR: feat: replace moment.js with date-fns (#214)
- Generated by: adr-generator assisted on 2024-11-03
```

## Example 2 — Good: No Alternatives Evidenced

This is what a correct retroactive MADR looks like when the diff only shows what was added, with no evidence of what was considered or rejected. The right move is to leave Considered Options empty and say so — not fill it with guesses.

```markdown
# Adopt Kafka for async event streaming between services

## Status

Accepted

> Note: This ADR was retroactively generated from commit history by adr-generator.
> Rationale accuracy depends on commit message quality. See linked commits to verify.

## Context and Problem Statement

Prior to this change, services communicated synchronously via direct HTTP calls.
The diff shows the addition of a Kafka producer/consumer setup across the payments
and notifications services, replacing direct HTTP calls in the event dispatch path.

## Decision Drivers

- No explicit drivers recorded in commit history.

## Considered Options

No alternatives recorded in commit history.

## Decision Outcome

Chosen option: **Kafka**, because the diff shows direct replacement of HTTP dispatch
calls with Kafka producer calls. No commit message rationale was recorded beyond
"add Kafka for async event processing".

Rationale not explicitly recorded. Implementation inferred from diff.

### Positive Consequences

- Services are now decoupled at the event boundary — visible in removal of direct
  HTTP client calls from payments service

### Negative Consequences / Trade-offs

- No trade-offs recorded.

## Links

- Commits: 9c2a881, 9c2a882, 9c2a883
- Merge/PR: feat: add Kafka for async event processing (#301)
- Generated by: adr-generator autonomous on 2024-11-03
```

## What NOT to Do

This is what a bad retroactive MADR looks like. The agent filled in Considered Options with plausible alternatives from general knowledge rather than from the diff. This is hallucination — none of these alternatives were evidenced anywhere in the commit history.

```markdown
## Considered Options         ← WRONG — none of these were in the diff or commit message

- Kafka (chosen)
- RabbitMQ
- AWS SQS
- Redis Pub/Sub
- NATS

## Decision Outcome

Chosen option: **Kafka**, because it offers better durability, replay capability,
and is well-suited for high-throughput event streaming compared to alternatives
like RabbitMQ which lacks log retention.   ← WRONG — fabricated rationale
```

The problem: a developer reading this six months later will treat "Kafka was chosen over RabbitMQ because of log retention" as a real decision that was made. It wasn't. It's a confident hallucination that poisons the decision record.

**The rule:** if you can't point to a line in the diff or commit message that shows an alternative existed, it goes in the empty list with `"No alternatives recorded in commit history."` — full stop.
